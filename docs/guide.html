Claude Code · ready-made setup

Claude Workspace Guide

One command gives any project a well-tested Claude Code setup. It adds good working habits, memory between sessions, and an honest note under each answer that says which tools Claude actually used.

version 0.13.0MIT licenceLinux · macOS · WSL · devcontainersgithub.com/Bey3fendi/claude-workspace

What's inside

Two well-known add-ons, each fixed to a version that has been tested together, plus one small piece of our own that ties them together, keeps the memory and gives your project a default CLAUDE.md.

our own · always on

workspace-core

Notices what kind of request you made (a bug, a new feature, tests) and points Claude to the right method. It also asks Claude to name a bug's cause before editing code, suggests when to clear the conversation, and writes the honest usage note.

working methods

Superpowers

Proven step-by-step methods: debug systematically, brainstorm before building, write tests first, check before calling something done.

memory · part of workspace-core

md-memory

Remembers earlier sessions in plain text files in your project's .memory/ folder: a running log, notes about parts of the code, and decisions with their reasons. It fills itself: a change that leaves no note gets a facts-only one, a designed change is asked to write down its decisions, and the notes for a file reach Claude before it changes that file. No background program, no database, no extra model calls. You can read, edit and commit the files.

keep it simple

Ponytail

“Lazy senior dev” mode: pushes Claude toward the simplest, shortest solution that works, with no extra layers nobody asked for.

coding guidelines · in CLAUDE.md

Karpathy guidelines

Guidelines that steer Claude away from the coding mistakes AI models commonly make, based on Andrej Karpathy's observations: think before coding, keep it simple, change only what you must, define how you'll check it worked. They come with the default CLAUDE.md, so they apply in every session.

There is also an optional model “router”. It is switched off and not installed unless you ask for it.

Install

Pick the way that matches how you work. All three end in the same place. Run them inside the project you want to set up.

Most people

One command

Needs Node 22+, git and Claude Code already installed.

In your project folder 
npx -y github:Bey3fendi/claude-workspace#v0.13.0 install --yes \
  --marketplace Bey3fendi/claude-workspace#v0.13.0
Containers

Devcontainer

Add one line to .devcontainer/devcontainer.json. Each new container installs Claude Code and the workspace by itself.

devcontainer.json 
"features": {
  "ghcr.io/bey3fendi/claude-workspace/claude-workspace:0": {
    "marketplace": "Bey3fendi/claude-workspace#v0.13.0"
  }
}
Working on the workspace itself

From a local copy

Use your own checkout. Changes you make show up the next time you start Claude.

In your project folder 
node /path/to/claude-workspace/cli/bin/claude-workspace.mjs install --yes

Then check it

Health check safe to run any time 
npx -y github:Bey3fendi/claude-workspace#v0.13.0 doctor
Every line should be a ✓, or a “-” for optional parts. A “!” is a warning worth reading. The last line says whether everything required passed.
Everything stays in the projectThe installer only touches files in your project folder; nothing is set up for your user account. Your CLAUDE.md gets one small block that points at the workspace's own instructions file; the rest of your CLAUDE.md is never changed, and uninstall takes only that block out. Prefer to keep your CLAUDE.md untouched? Add --no-claude-md, or --claude-md=local to use CLAUDE.local.md instead. Upgrading from a version before 0.8.0, which used claude-mem? Run remove-claude-mem once. It asks first and keeps claude-mem's saved data.

On Windows, use WSL. Native Windows isn't supported.

Day to day

Nothing new to learn. Start claude in the project and talk to it as usual. You'll notice five things.

  1. Claude picks a method that fits your request. “The total is wrong, find out why” leads to careful debugging. “Add a pause menu” leads to brainstorming first. “Write tests for…” leads to test-first work.
  2. On a bug, Claude names the cause before editing. If it tries to change code before saying what's actually wrong, the first edit is held back and Claude is asked to state the cause first. It's held back at most twice; edits to tests and docs are never held.
  3. A short note appears under each answer. It shows what really happened, based on what Claude Code recorded rather than on what Claude says about itself. Only you see it; Claude doesn't.
  4. Plans are carried out in this conversation. When Claude works through a written plan, it does every task itself, right here, and asks one fresh reviewer to check the whole result at the end. It doesn't hand each task to a separate helper with its own review, which costs much more. You won't be asked which way to run a plan.
  5. Ask for an explanation with /explain. Claude writes a short note on what changed, why, what was not tested and where to start reading, built from facts the workspace records itself (the changed lines, the commands that ran). You see the two-line summary; the full note is in .explain/, which stays on your machine. /explain HEAD explains your last commit. Nothing happens unless you ask.
  6. Helpers never use the most expensive model. Any helper Claude starts, including that final reviewer, runs on at most Opus 5.5 at high effort, even when a skill asks for "the most capable model". Cheaper choices are kept, and your own conversation is never changed. To turn this off, set CW_SUBAGENT_CAP=0.
  7. In very long conversations, Claude suggests a fresh start. Past about 300,000 tokens it recommends /clear or /compact and first writes a handoff into the session log. More on that below.

What the note under an answer looks like

… Claude's answer …

Verified by engine: activated systematic-debugging · root-cause gate held 1 edit · report matches engine events (activation = instructions loaded, not proof they were followed)

“Activated” means the method's instructions were loaded. It doesn't promise Claude followed every step. The note is careful to say only what it can prove.

Clear or compact?

A long conversation gets slower, costs more and gets less sharp. When that happens, Claude will end an answer with a recommendation and a handoff note in a box.

/clear usually best

  • Starts a fresh, empty conversation.
  • Claude has already saved the handoff in .memory/session.md, and the new conversation loads it by itself. Nothing to paste.
  • Cheaper and sharper than a long summary.

/compact

  • Squeezes the current conversation into a summary.
  • Pick it when something can't be written down easily, like a long chain of reasoning in progress or a large paste you haven't saved.
  • workspace-core reminds Claude afterwards which method it was using, and the session log is loaded again.
  1. Claude says CLEAR (or COMPACT) and gives a one-line reason.
  2. Claude adds the handoff to .memory/session.md. It covers the goal, what's done, the decisions, the dead ends, the next step and the files involved.
  3. Type /clear and carry on. Claude picks up from the log.

Claude only suggests this at a natural pause, when a piece of work is finished, never in the middle of a task.

Turning things off

Each extra can be switched off with a setting, for one session or for good. For one session, put it in front of the command, e.g. CW_GATES=0 claude. To make it permanent, add it to your shell profile.

SettingWhat it turns off or changes
CW_CONTRACTS=0Matching methods to your requests (and the reminder after compacting)
CW_GATES=0“Name the cause before editing” on bugs
CW_CONTEXT_PRESSURE=0The clear-or-compact suggestion
CW_CONTEXT_PRESSURE_TOKENS=250000How long a conversation gets before the suggestion (default 300,000)
CW_LISTING_TRIM=0Keeps rarely-useful skills in the list Claude sees
CW_MEMORY=0md-memory (nothing loaded or added to the conversation)
CW_MEMORY_AUTOLOG=0The facts-only note the workspace adds when a change leaves none
CW_MEMORY_NUDGE=0The end-of-request reminder to write down a design's decisions
CW_MEMORY_PREEDIT=0Holding a first edit until Claude has seen the notes for that file
--no-claude-md (install option)The default CLAUDE.md block, and with it the Karpathy guidelines
CW_PLAN_EXECUTION=0Stops telling Claude how to run plans. Running each task through separate helpers stays blocked; to allow it, remove its line from policies/skill-denies.json.

If you already have your own clear-or-compact hook (a hook named “context-pressure”), the workspace sees it and stays quiet, so you never get two notes.

Update & roll back

Each release is a numbered version on GitHub, and a project stays on its version until you move it.

Move a project to a new version 
npx -y github:Bey3fendi/claude-workspace#v0.13.0 repair \
  --marketplace Bey3fendi/claude-workspace#v0.13.0
Change both v0.13.0s to the version you want. The workspace remembers your last five versions.
Going back 
npx -y github:Bey3fendi/claude-workspace#v0.13.0 rollback
It prints the exact command to run, without running anything itself. Check the command, then run it.

Privacy & safety

Stays in your project

Only a few settings files in the project change. Your code is never touched. It refuses to run over unsaved changes in those files unless you say so.

Fully reversible

Uninstall puts every file back exactly as it was. If you edited a file afterwards, only the workspace's own lines are removed.

No extra services

Memory is plain files in your project, read by Claude Code like any other file. There's no background service, no database and no memory telemetry.

No secrets stored

No keys, logins or tokens are written into the project or printed. Your Claude login stays where Claude Code keeps it.

When something's off

Doctor shows a red line

Run repair. It puts back whatever is missing and fixes plugins that have moved off their fixed version. Then run doctor again.

“Uncommitted changes in files the workspace would modify”

Commit or stash your changes to .claude/settings.json, CLAUDE.md or .gitignore first. If you're sure, add --allow-dirty. A backup is still taken.

“Claude Code 2.1.x (tested: …)”

Claude Code updated itself to a version this release hasn't been tested on. It's a warning, not an error, and things normally keep working.

No method was used on my request

The request didn't sound like a bug, a feature, tests or a review, so nothing was added. Using a clear word helps (“bug”, “add”, “write tests”, “review”). You can also ask for a method by name.

Memory doesn't seem to work

Run doctor and look at the memory lines. If a file or the permission rule is missing, run repair. Claude writes notes at natural pauses, so a fresh project's log only has its header. You can open .memory/session.md to see what it remembers.

For you, the maintainer

Shipping a release

  1. Raise the version to the same number in three places: package.json, workspace.lock.json (workspaceVersion) and devcontainer/src/claude-workspace/devcontainer-feature.json. If workspace-core changed, also raise plugins/workspace-core/.claude-plugin/plugin.json, so repair picks it up.
  2. Run npm run gen:marketplace and npm test.
  3. Commit, then tag: git tag -a v0.13.0 -m "…" and git push origin main v0.13.0.
  4. GitHub then runs the tests and publishes the devcontainer feature automatically. Check the Actions tab.
Never move a published tagProjects are pinned to it. If a release is broken, ship the next number instead.
